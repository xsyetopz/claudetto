### Handoff Hooks (`session-handoff`)

- Register `classic.SessionEnd` and `classic.PreCompact` in `archive/plugins/claudetto/hooks/register.ts`. Each calls one writer in `archive/plugins/claudetto/modules/session/handoff/`. The `SessionEnd` rule filters on reason `clear`. Why: both events exist in the installed `2.1.312`, in the event list at `chunk-b30aq3ej.js:1475` of 33 names (`cc-inspect` `surface` `hook-event`, re-read on 2026-10-28, because the install moved from `2.1.311` to `2.1.312` on 2026-10-27), and the docs list the reasons `clear`, `resume`, `logout`, `prompt_input_exit`, `other`.
- The writer reads the transcript file, not `$.session.messages()`. Why: the free stub-mod probe of `archive/tasks.md`, old task 2.1 ran `session.end`, `classic.SessionEnd`, and `classic.SessionStart` headless and `$.session.messages()` threw in each one, "no session is bound in this process (the REPL has not mounted and no headless session is built)". `$.fs.write` worked in each one, and `classic.SessionEnd` carried `transcript_path`, so the transcript is the one source that both modes have (`references.md`, Stub-Mod Probe). Task 4.3 then measured the interactive case: during a typed `/clear` the session is bound and `$.session.messages()` answers in both halves of `SessionEnd`, while on `prompt_input_exit` it throws (`references.md`, "The Interactive `/clear`, Measured in the REPL"). The writer still reads the transcript, because that is the source every path has, and the same run showed that the budget the hook reports is not the one it is cut at.
- The code-built writer must finish in 1,500 ms of wall clock, and 10,000 ms is the most any declaration can ever buy it. Two bounds act together, and the `archive/tasks.md`, old task 2.9 lab measured both.

[], ...(qh() ? [] : q7()?.SessionEnd ?? [])]`. ### Window Budget (`window-budget`)

- One module, `archive/plugins/claudetto/modules/window/`, with a recorder (`session.measure` handler), a fit (pure function over rows), and a report (a skill that prints the table). No private file: rows live in `$.store`.
- The recorder is the `session.measure` handler and reads no op of its own. The token counts exist in `session.measure` itself, as `context.tokens`, the same figures `$.session.usage()` answers. The source is `plugins/claudetto/.claude-plugin/types/claude-code/index.d.ts`: line 11814 for the event's input, 11609 for `SessionContextUsage`, 11807 for the doc that says so. The stub probe of `references.md`, "Stub-Mod Probe", was inconclusive not because the field is missing but because `context.tokens` is absent until the first response of the live window (line 11605), which a headless stub never had. `session.measure` gives the window points and the context fill, and `turn.complete` gives what a turn really cost. `context.tokens` is the whole prompt of the last response (line 11611: uncached, cache-written, and cache-read together), so a `session.measure` row can carry no output tokens and no cache split. The recorder does: `turn.complete` has `usage` (line 14322), a `TurnUsage` (line 14685) of the four `ModelUsage` counts (line 6618), `input_tokens`, `output_tokens`, `cache_read_input_tokens`, and `cache_creation_input_tokens`, plus the model, summed over the turn's responses (line 14683), and absent when nothing counted. The turn rows live in `$.store` under `window.turns`, written by `onTurnComplete`. The weight divides the first by the second: the points of the measure rows over the input-side tokens of the turn rows (`input_tokens` plus both cache counts, never `output_tokens`, because the line says per 1,000 input tokens). The context fill is not a denominator because it is the whole prompt at every response: summing it over the turns of a task counts the same prompt again at each turn, so the sum grows with the square of the conversation and the weight comes out too small by a factor that depends on the context length. A row holds the input tokens, the window, the percent, the points the five-hour window moved, and the dollars from `cost.usd` (line 11639). The event fires when a unit moved (line 4555) and `rateLimits` moves in whole points (line 11835), so the last five-hour reading is kept in `$.store` and the points of a row are the delta against it.
- Rows live in `$.store` under `window.rows`, newest last. A row is dropped once it is older than `KEEP_MS` of `window.ts`, which is the seven-day window: line 12003 names `five_hour`, `seven_day`, and a gateway's `spend_limit` as the kinds the engine reports, so a row older than the longest of them prices nothing the user still has to spend. The bound is that window and not a count of rows, because a count would be a number picked to fit the 4 MiB of JSON the store refuses past (the doc of `$.store.set` in the same file) and it would keep rows that price nothing. `window.last` holds the reading the next delta is taken against, and `window.usd` the dollars of the session so far. A login with no five-hour window, such as an API key, gets no row and still has `window.usd` (`rateLimits` is empty there, line 11824). The first reading, and a pair that spans a reset (`resetsAt` differs, or the percent went down), give no row and only set the base.
- The source tag of a row comes from the engine's own events and not from a marker of ours, because `SessionMeasureInput` has no source field. `turn.start` says `main` or, with an `agentId`, `subagent` (line 14385), and `session.compact` brackets a compaction whose summarizer request the session ledger holds (line 11441). The loops running are a list in `window-hooks.ts`; the newest is the source, and the task of a row is the id of the main turn under it, so a subagent's rows add to the task that spawned it. Two limits are stated and not hidden. `handoff` and `classifier` are in the type but nothing sets them: our handoff writers make no model call, and neither the auto mode classifier nor the Jev call leaves an event that names it. A background subagent that overlaps a main turn can take the tag of the newest start.
- The report is `window-report.ts`. Points per task are the sum over its turns, and a figure from a single row prints "too few rows", because one row is one reading of the window rather than a sum. The weight per 1,000 input tokens prints "not measured" where there is nothing to divide, which is no measure row or no turn that reported tokens, and a saving does the same; otherwise a saving is printed in points of the five-hour window and never as a share of a plan limit. There is no row minimum beyond that. A threshold would be a number with nothing behind it, and the honest form is to print the figure with the count of turns it rests on beside it, so the reader weighs it. The weight is a plain ratio of points to tokens, not the fit, which stays open.
- The unit is the turn row. How rows group into a task and how the weights are fitted (a least-squares fit is one candidate and not a choice) come from reading Botfarm and `claude-hud` (`archive/tasks.md`, old task 9.3). Nothing is decided before that.
- The method, `archive/tasks.md`, old task 9.3, after reading both trackers. The finding is negative: neither Botfarm nor `claude-hud` turns a series of rate-limit readings into a per-unit-of-work number, so there is no method to copy, and none is made up here. A Hermes agent read them on 2026-10-28 and marked its own line numbers unverified, so I downloaded eleven files of the two pinned commits and re-read and re-grepped them in the main session. Both work on the absolute percentage.
  - `claude-hud`, MIT ("Copyright (c) 2026 Jarrod Watts"), at commit `cf95a322afd18db045175d28962650ae7392ed77` of 2026-10-26. It reads the status-line stdin: `const limits = stdin.rate_limits;` at line 179 of its `src/stdin.ts`, then `limits?.five_hour?.used_percentage` and `limits?.seven_day?.used_percentage` at 180 and 181, and `limits?.five_hour?.resets_at` at 188. It keeps no history of readings, so it computes no delta: its pace is a projection of the one current value, `const elapsedFraction = (windowMs - remainingMs) / windowMs;` and `const projected = percent / elapsedFraction;` at lines 42 and 43 of its `src/usage-pace.ts`.
  - Two things of `claude-hud` we do take, both with a line. First, a floor below which it reports nothing: `const MIN_USED_PERCENT = 10;` at line 11 of its `src/usage-pace.ts`, compared at line 38. Second, the hazard its transcript reader handles, which our recorder must handle too: one assistant message can yield several usage records, so it keys usage by `entry.message?.id` and merges by the maximum of each field rather than by adding, `this.usageById.set(id, previous ? maxUsage(previous, usage) : usage)` at line 238 of its `src/transcript.ts` with `maxUsage` at 451, and it adds up only when a record leaves the cache or at the end, lines 242 and 421. An adding recorder would double-count a streamed turn.
  - Botfarm is `AlexDobrushskiy/botfarm` at commit `775a439cb5bd248da2933c0047ab827fb4342f91` of 2026-04-16, and it is not a code source for us: its `LICENSE` is "Business Source License 1.1", which is not open source, the same ground on which `references.md` rejects `context-mode`. Only its observed behaviour is cited. It polls `https://api.anthropic.com/api/oauth/usage` on a fixed interval, `DEFAULT_POLL_INTERVAL = 600` seconds at line 46 of its `botfarm/usage.py`, capped when throttled by `MAX_ADAPTIVE_POLL_INTERVAL = 1800` at line 61. It stores the absolute fraction, `raw_5h = five_hour.get("utilization")` then `self._state.utilization_5h = raw_5h / 100 if raw_5h is not None else None` at lines 759 and 760, and it uses it only against a threshold, `DEFAULT_PAUSE_5H_THRESHOLD = 0.85` at line 49, compared at 150 and 151. Its dashboard aggregates by averaging inside time buckets rather than by differencing, `"  AVG(utilization_5h) AS utilization_5h,"` at line 680 of its `botfarm/db.py`. A `grep` over its five Python files, which `wc -l` totals at 6882 lines, finds "delta" only in its Retry-After parsing at lines 116 and 117 of `botfarm/usage.py`, which confirms that it holds no delta logic at all.
  - So the method is ours, and these are its parts, each either sourced or marked. The quantity is the delta of `five_hour.used_percentage` between two readings, because the absolute value answers "how much is left" and only the delta answers "what did this work cost", and no source offers a third option. The unit stays the turn row, as above. A pair of readings whose `resets_at` differs spans a window reset, so its delta is meaningless and the pair is dropped rather than clamped: this is our rule, taken because neither tracker has reset handling to copy, and `resets_at` is in the payload both of them read. There is no row minimum before a weight is reported, for the reason the report row above gives: a minimum would be a number with nothing behind it, so the figure prints with the count of turns it rests on beside it. The fit is still open, as the row above says.
- A rule that spends the window by what is left is not designed here. The rows of `window-budget` decide whether to build one, and a source must back its design.
- Value of the record beyond this change: it prices every later decision in window points. The cheap-model probe, the tier values, and the prompt cuts each report in points once rows exist. This is what turns "optimize the usage window" from a claim into a measurement.
- Free to build and run: `$.session.usage()` costs nothing on a plain call (docs). No paid run is needed to start recording.

And that charge is not the context size in disguise, which was the one objection that could have flipped the answer: at a fixed prompt size of 60,000 to 100,000 tokens the edit rate within 40 turns of a compaction is 57% of the steady rate over 689 and 1,074 requests, while the steady rate barely moves across four size bands. What a paid run can still add is the full separation, which task 10.5 carries.
- What a compaction leaves behind is modelled as a fixed block plus a summary, not as a flat share, because a flat share breaks away from the threshold that produced it: 8.07% of 80,000 tokens is less than one summary. The parts are measured over all 36 boundaries, 11,760 tokens of system prompt and tool schemas plus 0.0288 tokens of summary per token compacted, which reproduces the measured 8.07% at 225,000 and gives 17.6% at 80,000 (`docs/evidence/compaction/threshold.md`). Fitting the two parts by least squares instead was tried and rejected, because every real boundary fired at one threshold: the line had no leverage and predicted a negative context.
- The one lever that moves the moment rather than the threshold is sleep compaction, and it is undocumented: `CLAUDE_CODE_SLEEP_COMPACT` queues `/compact` while a session idles, its timer "fires at 0.9 of the cache time window", `CLAUDE_CODE_SLEEP_COMPACT_AFTER_MS` is clamped between 60,000 and 210,000 ms, and `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` sets the size at which idle compaction applies (`clawdipedia` `configure/env-vars/context-and-compaction`, read 2026-10-28). By that design it compacts while warm so that a late return reads the summary and not the whole window, which is the opposite of how the Developers Digest article frames it (`references.md`). None of the three keys is set on this login. Whether the new tree sets any of them is a key decision with its own row and no value until rows price it.
- Whether the new tree keeps writing `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` is open, and it is a `surface-trim` decision and not a compaction one. The setting exists only to pull the harness's threshold down to `HANDOFF_TRIGGER_TOKENS`, and the new `session-handoff` spec writes the handoff from `classic.PreCompact`, which the harness awaits before the summary request, so the ordering the override once protected no longer depends on it. Task 2.4 decides it with the other keys.

## Risks / Trade-Offs

- [A code-built handoff loses detail that a model summary keeps] -> The probe measures rereads (the bars of `archive/tasks.md`, old task 8.5), and the Claude-written file is the primary writer.
- [`SessionEnd` cannot read the messages on `/clear`] -> The transcript fallback, or the rolling write per turn. `archive/tasks.md`, old task 2.1 settles it before code.
- [A tier row sets a key that the installed version ignores] -> The pin test per key, and `claude plugin validate --strict`.
- [Thread numbers are self-reports and may not hold here] -> They set starting values only. Cost per task against plain Claude Code, from a paid eval, decides (M1).
- [Removing `model:` from agent files raises the cost of `Apollo` and `Artemis`, which use Haiku today] -> The tier row sets `CLAUDE_CODE_SUBAGENT_MODEL` and this file names no model. The audited model and effort rows are in `docs/models.md`, and the `mainModel` field of the tier row settles whether `opusplan` stays, which task 8.1 writes. Check with `/tasks` that the subagents run on the row's model, as one thread did.
- [A hook writes an edited file after the agent's own edit, so the agent's context is stale] -> No rebuilt hook writes a file the agent just edited. The heading rewriter of the `hygiene` slice was removed on 2026-10-27 for this reason, and the heading convention is kept by the reply-side note, which writes nothing. See `references.md`, "Three Hooks Removed on 2026-10-27".
- [Cache read weight against plan limits is unknown] -> Report dollars and the `/usage` share, not a plan promise.
- [The rebuilt observer spends tokens on notes that do not help the code] -> It ships off, the topic rule is the coding test of G16, and the tier row turns it on only against `window-budget` rows. A check that offers nothing costs one bounded call and no window read.
- [Our own prompt text is worse than the one we may not copy] -> The quality of an offer is judged by the person who answers it, and the answer lists are the record. A paid quality comparison is not run, because the original cannot be run side by side without turning on the plugin we are replacing.
