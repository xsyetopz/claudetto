## Problem

Claudetto should cut the usage and token cost of Claude Code, with little loss of capability. Today it mostly works around the harness and keeps its own large layer on top.

Facts from this repo (sources in `architecture.md`):
- The plugin has about 20,700 lines of runtime code, 47 hooks over about 30 events, and 9 private stores (the earlier plan `epic-a-complete-restart-sunny-conway.md`, measured with `wc`). Several built-ins already cover its work: compaction, goals, checkpoints, auto mode.

- A 1-hour subagent cache plus a keepalive ping cut one user's weekly burn by about 60%. The author's edit says tokens rise slightly and only the billing shifts.
- Subagents start cold and re-read files. A hard cap on subagents and "stop after the same fix fails twice" are common advice.
- The Anthropic article gives no token or cost figures. It says a single loop with skills often beats subagents on quality, cost, and latency. ## Users

- A Claude Code user on Pro, Max 5x, or Max 20x who hits the 5-hour or weekly limit.
- The maintainer, who wants one small plugin that is cheap to keep.

## Goals

- G1: Lower cost per finished task against plain Claude Code, without a drop in correctness.
- G2: Scale by subscription tier. Each tier gets its own subagent cap, subagent model, main model and effort, context cap, and handoff threshold.
- G3: Never lose a session silently. A typed `/clear`, an exit, and a compaction each leave a short handoff, and a failure to write one is visible.
- G4: Replace a measured-costly path with the cheaper one. Choose handover or compaction by a measurement on a cheap model, not by opinion.
- G5: Do by mod or hook whatever a mod or hook can do. Override a built-in instead of working around it, where a documented or probed surface exists.
- G6: Keep the added prompt text small, stable, and under a tested size limit.
- G7: Keep the repo small. Drop code that a built-in covers. No wiki.
- G8: More finished work per window. The five-hour and weekly windows are a budget like tokens are. Claudetto measures what a task costs in window points. Whether a rule that spends the window by what is left is worth building is decided from those rows (which waits on the rows of `window-budget`), and none is designed before then (user, 2026-10-27: "More work for less cost").
- G9: Look forward. Each gap the work finds gets a long-term fix in the specs, not only a note. A gap with no fix yet names the measurement that will give one.
- G10: Invent nothing. Every requirement, value, and default cites a doc, a measurement, or code under a license we may borrow. A gap with no source becomes a measurement task or sits under "Held Back until Sourced", and is never filled by a guess to satisfy a spec (user, 2026-10-27: "You shall not be allowed to invent / make up something no matter the circumstance, and no matter what it is. It is absolutely forbidden." and "Making things up just to satisfy 'a spec' is forbidden.").
- G11: An agent finishes the read or the work it was given, or reports exactly what blocks it. It does not stop early with "partial coverage" or wait for approval of a free step (user, 2026-10-27: "your laziness is counterproductive. You *must* keep working." and "Big problem for claudetto to solve."). Evidence from this session: dossier reads A, C, D, F, and H each returned with partial coverage and a note that files were not opened, and one `Hephaestus` agent ended after one `Bash` call was denied by the `head` rule of a project hook. The cause of each is unmeasured, so `archive/tasks.md`, old task 13.1 finds it before any rule is written.

- G12: Golf the harness. Claudetto is Claude Code golfing: the fewest characters of prompt, config, and tool definition that still finishes the task (user, 2026-10-27: "think of claudetto as \"claude-code-golfing\". code/prompt-golfing."). Two games set the pattern. Code golf is "a recreational programming competition where the goal is to solve a problem using the shortest possible source code (measured in characters, bytes, or keystrokes)", and the user accepts its cost: "Who cares if it's dense, cryptic, and possibly unreadable. As long as it's maintainable by ai agents, it's fine." Prompt golf scores the prompt, and its own page says "In prompt golf, you instead try to write the shortest prompt for a Large Language Model (LLM)" and "It's only natural that for prompt golf, the goal should be to minimise the number of tokens" (`promptgolf.app/about`, read 2026-10-27). The score is characters sent per finished task, and the acceptance test stays M1, billed cost per finished task, because one study cut 38.4% of delivered tool-output tokens and raised billed cost by 6.8% (arXiv 2607.12161, `references.md`). A shorter score that costs more is not a win.
- G13: CLI and TUI only. Every surface that exists for claude.ai, the web app, mobile, the cloud, or onboarding is turned off by a documented key or a deny rule, as far as Claude Code allows (user, 2026-10-27: "claudetto will disable as many surfaces as claude code allows, such as the builtin skills, claude.ai sync, artifacts, design, whatever garbage nobody really needs. claudetto is only for the CLI/TUI."). `Workflow` goes in particular, because the project uses worktrees and the tool serves Dynamic Workflows (user, 2026-10-27: "we use worktrees, not workflow. workflow tool is for Dynamic Workflows, which eat tokens like crazy."), and the reading above puts its definition at 5,355 characters, or 22,310 with `disableBundledSkills` set. A key that would stop claudetto itself, or a command the user needs to run the CLI, is not written. The list and the reason for each are in `docs/surfaces.md`.

- G14: Five verbs, in this order. Override it, disable it, recreate it, optimize it, trim it (user, 2026-10-27, as five lines each ending "Yes we can, and yes we will!"). Override comes first because a mod beats a workaround (G5). Disable comes next because an unused surface costs characters (G13). Recreate comes only when the feature is worth having and the built-in version carries telemetry, a non-CLI path, or an unnamed model, which is the case for `cc-plugin-you-should-know@builtin` (`specs/builtin-rebuild/`). Optimize and trim come last, measured by the golf score (G12).
- G16: The test for every piece is coding. The user set it on 2026-10-27: "the keyword for our needs is this: \"does it help coding? no? then it gets dropped without hesitation\"", and gave the reason from the product's own name: "it's *literally* in the harness' name: Claude *Code*. it's *only* for coding." The illustration the user chose is the pronouns paragraph of the system prompt: "a *customer service agent* needs to know about pronouns. a *coding* agent does not. *coding* is the ultimate word here." This goal differs from G13, which turns off a surface that is not the CLI. G16 drops text and features that are inside the CLI and still have nothing to do with writing software. Three decisions already rest on it, each recorded with its measurement: `includeGitInstructions: false` for `638` characters ("this is a win. it has nothing to do with real coding, thus unnecessary"), fast mode off by `fastMode: false` and `CLAUDE_CODE_DISABLE_FAST_MODE` ("speed is not our concern. too many tokens it consumes. if something costs too many tokens and usage, it either gets trimmed, or dropped"), and four non-coding passages of the system body totalling `901` characters, which is 16.0 percent of it (`docs/prompt/overrides.md`). The order of the verbs still holds: trim first, drop when a trim leaves nothing worth keeping.
- G15: Each tool, skill, and built-in plugin we keep is a decision the user made on a written page, not a default we inherited. One file per item under `docs/keep/`, with what it does from the docs, what claudetto needs it for with file and line, its measured request cost, and a recommendation. The user picks from those pages (user, 2026-10-27: "you may ask user here for what tools to keep by creating a .txt for every single tool, pros/cons from cc-docs, and what user actually does that considers whether these are worth or not, and what claudetto will need for what purpose, if any." and "the same applies to skills, `...@builtin` plugins.").

## Success Measures

- M1: Cost per finished task against plain Claude Code on the same task set, measured by a paid eval after the user approves it. The measure is cost, not context size. Each task set runs more than once, because one fold changed a result in one of two runs.
- M2: A test fails on the old code and passes on the new: a typed `/clear` after a short session leaves a handoff file, and the next session receives it.
- M3: Each silent failure in G3 has a log line and a test.
- M4: A byte budget for each prompt piece, checked by test: `agents/main.md` (10,865 bytes now), `Concise.md` (2,407), each skill `description:` line (ten skills, 155 to 194 characters now, 1,720 in all), and each injected hook string. The totals fall against the numbers in `architecture.md`.
- M5: A tier table with one row per tier, tested for each key it sets. Each key is checked against `schemas/` or the installed binary first.
- M6: The probe table (B, H, C, with a cheap-model H arm) shows cost per arm and its share of the weekly limit, and the decision follows the rule in `design.md`.
- M7: `just check` passes with no wiki step, and `claude plugin validate --strict plugins/claudetto` passes.
- M8: Tasks finished per 10 points of the five-hour window and of the weekly window, from rows that the mod records (`window-budget`). The first baseline is plain Claude Code on the same tasks.
- M9: The weights of a cache read, a cache write, an input token, and an output token in window points per million tokens, for this login, with the row count behind each. Until the rows exist the answer is "not measured".
- M10: The golf score. Characters of the first request of a session, split into `system`, `tools`, and `messages`, read from the request body that a local fake API captures. The run needs no model call, so the score is free to take on every change. The start is the 42,676 characters of the empty-settings reading, and each row of `docs/surfaces.md` names the settings that produced it. A change that raises the score states why the capability is worth it.
- M11: No non-CLI surface in the request. The reading on the real login lists every tool the request carries, and each one that serves claude.ai, mobile, the cloud, or onboarding is denied or keyed off, or carries a line saying why it stays.
- M12: Classifier calls per task. The count of auto mode classifier requests in a real session, divided by the tasks finished in it, from the `classifier` rows of `window-budget`. One call is larger than three first requests (`docs/prompt/machinery.md`), so this count is read next to M10.

## Held Back until Sourced

These values and claims were stated as fact in this change with no source. Each is removed from the specs and design, gets no task until a source exists, and is never filled by a guess (G10).
- A default tier row for a tier that is not in the table. `specs/tier-profiles/spec.md` wrote the Pro row for it. The code does the opposite today: `planCap` in `archive/plugins/claudetto/modules/setup/domain/plan.ts` returns `cap: undefined` and the tier it read.
- A figure for the share of the weekly limit that is "now" used, which `architecture.md` stated with no date and no statement of what it is a share of.
- The claim that Pro, Max, and Team plans are not charged for classifier overhead. `specs/low-hitl/spec.md` cited a "claude.com article" with no URL and no date, and a `search_docs` call for "classifier cost" over `clawdipedia` on 2026-10-27 found no page that says it. Measure `M12` counts the calls and does not depend on it.
- A rule that a git remote is a "trusted repository" in `autoMode.environment`. No source names it, and the same requirement forbids inventing a rule.
- A length cap on the `deny` reason of `agent.spawn`. The page `extend/mod-api/agent` types `AgentSpawnResult.deny` as a `string` and gives no cap.
- A count of prompts per hour as a quality measure, which `specs/low-hitl/spec.md` held before this list did. No source gives a target rate, so `M12` counts calls instead.
- A second proposer of allow rules. The program already has `/fewer-permission-prompts` and `/auto-mode-setup`, and no source says a second proposer beats them.
