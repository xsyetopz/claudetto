# Design

## Context

See `proposal.md`, "Why", for the motivation. Each fact below names its source.

- Baseline `62e2fe96`, Claude Code `2.1.318`, Bun `1.4.4`. Sizes: `plugins/claudetto/src` holds 23,266 lines, tests included, and 16,079 non-test `.ts` lines. 23 blocks are attached in `src/blocks/catalog.ts`, and `plugin.json` declares 20 `userConfig` keys. `claudetto-you-should-know` holds 1,257 source lines (`ISSUES-2026-11-04-1500.md`, "Baseline"; recounted with `wc -l` and `plugin.json` on 2026-11-04).
- Baseline checks: `lint` fails on `commitlint` over two existing commit bodies. `test` gives 1,776 pass, 7 fail, and 2 errors, all from the limits of the baseline's `confine` wrapper that this session's `Bash` runs under: `mkdtemp` in `~` gets `EPERM`, and `pty` and `tmux` runs fail (`/tmp/claudetto-baseline-test.log`; causes in `ISSUES-2026-11-04-0934.md`, "`just check` on 2026-11-04"). `typecheck`, `validate`, and both labs pass.
- A plugin is a mod when `hooks/hooks.json` holds `modules` (`code.claude.com/docs/en/plugins/mods/reference`, "Files"). The baseline plugins already are mods.
- A plugin's root `settings.json` applies only `agent` and `subagentStatusLine` (`code.claude.com/docs/en/plugins/components.md`, "Default settings").
- A `settings.read` hook can replace keys in the session's merged settings on Claude Code ≥ 2.1.304. A key that Claude Code reads per source, such as `env`, does not change. Under managed settings or a Team or Enterprise login, a built-in guard can skip the hook (`code.claude.com/docs/en/plugins/mods/events.md`, "Change or refuse a settings read"). Probe 2.1 on `2.1.318` in `-p` mode: of the tier keys, only `disableBundledSkills` changed; `model`, `effortLevel`, `outputStyle`, `permissions`, `env`, and `enabledPlugins` kept the file values (`ISSUES-2026-11-04-1500.md`, "Probe 2.1").
- Hook time limit: 10 s of a hook's own time per event. `$.process.run`: 30 s by default and 10 min at most. `$.store`: 4 MiB (`plugins/mods/reference`, "Limits").
- The 7 upstream OpenSpec skills installed in this repo total 116,067 bytes (`wc -c .claude/skills/openspec-*/SKILL.md`).

## Goals / Non-Goals

**Goals:**

- One hooks module per plugin, with plain `on(...)` calls and no block, catalog, or ports layer.
- Every feature row in `feature-map.md` reaches a fate decided by its named check.
- Parity tests that pass against both the baseline and the rebuild.

**Non-Goals:**

- Patching the Claude Code binary or its package (`AGENTS.md`).
- Rewriting `tools/` or the evals, beyond what `just check` needs to run. The in-repo probing tool left this repo under task 17.13; its evidence is in `evidence/`.

## Decisions

### 0.4.0 is a restart with its own layout

The user set this on 2026-11-05: 0.4.0 is a restart. It has no option aliases, and its internal structure is designed fresh. The layout follows the mod docs (the `plugin-authoring` skill on 2.1.318). The hooks module is `hooks/register.ts`. Each feature is one `hooks/<feature>.ts` that exports its `on(...)` calls, with its lab tests beside it as `<feature>.test.ts`. Pure parts go in `hooks/<feature>/` only when the feature file would pass about 300 lines. Every text the model reads is in `hooks/texts.ts`, so one file holds the measured text. An event that two features hook unmatched is owned by `register.ts`, because the engine loads a module only with one unmatched hook per event (probed 2026-11-05: `on("session.start") is registered twice without a matcher`, and the module "failed to load" on a `tool.check` pair). The status line is a separate program, `bin/claudetto-statusline` with `statusline/`.

### Rewrite the structure

Each plugin is rewritten as one hooks module, from a clean slate (above, "0.4.0 is a restart"). No 0.3.0 test file, option alias, or migration is carried (`ISSUES-2026-11-05-2100.md`:51). The gate's shell parser, `hooks/gate/shell-words.ts`, is kept as code (goal item 2), with tests written for 0.4.0. The layers that only wrapped `on(...)` are gone: `blocks/`, `catalog.ts`, `declare-after-start.ts`, and `Ports`. Check of 2026-11-06: `find plugins -type d -name parity` prints nothing, and `grep -rn -i -e "before the rename" -e "0\.3\.0" plugins` finds no match outside `node_modules` except `hooks/gate/refs.test.ts:12`, a git-ref fixture (`git reset --keep release/0.3.0`), not migration code.

### Settings reach the session by the narrowest route that a probe confirms

1. `subagentStatusLine` ships in the plugin's root `settings.json`. That is native and needs no setup step.
2. `/claudetto:setup` writes the tier keys to a settings file, as the baseline does. Setup becomes one implementation, the in-session command. The `bun src/tiers/setup.ts` CLI is removed.

Alternative: serve the tier keys from one `settings.read` hook, so setup writes nothing and uninstalling removes them. Rejected for 0.4.0 by probe 2.1: in `-p` mode the hook changed 1 of 7 measured keys. Claude Code reads `model`, `effortLevel`, and `modelSettings` once at session start (`code.claude.com/docs/en/settings.md`), and the docs exclude permission rules and `env`. One key alone does not justify a second route. If the interactive half of the probe shows more keys taking effect, this decision is reopened.

### The gate keeps only what native rules cannot express

The gate is reviewed one rule at a time against `permissions.deny`, `sandbox.filesystem`, and `autoMode`. (Since goal item 3, setup turns on the built-in sandbox with a short `sandbox` block; see "Sandbox (goal item 3)".) A rule that a native setting covers on the gate's own lab fixtures is removed. The rest stay in one `tool.check` hook. The false positive "`\.env` in code text read as an env-file read" (`ISSUES-2026-11-04-0934.md`) becomes a fixture that must pass. The repeat-denial stop and the retry after a denial stay. Probe 2.8 measured `permissions.deny` on the fixtures. Deny rules stop each rule's plain form, and they miss `sh -c` and `bash -c` bodies, `git -C`, command substitution, `export -p`, and redirects or `tee` into `/etc`, so those parsed-shell rules stay. Probe 2.8a measured `ask` rules. They ask on the same plain forms and miss the same parsed-shell forms, and Claude Code's built-in checks already ask on `rm -rf` of `/` or `~` in every form and on writes into `.claude/` and `.git/hooks/` (`ISSUES-2026-11-04-1500.md`, "Probe 2.8", "Probe 2.8a"). So setup can write the plain `ASK_*` forms as `permissions.ask` rules. The gate keeps the parsed-shell forms of each `ASK_*` rule, and it drops the `ASK_PROTECTED` asks for `.claude/` and `.git/hooks/`, which the built-in check already asks. `DENY_ROOT` stays a deny, because the built-in check only asks, and the gate only tightens a verdict. Claude Code runs hook commands through `CLAUDE_CODE_SHELL_PREFIX` too (observed).

The rewrite carries these gate behaviors as they are (`gate/block.ts`, inventory `a750589b303363dc5`):

- It only tightens a verdict, and it reads only the `command`, `file_path`, `notebook_path`, `path`, `pattern`, and `glob` fields, so `Monitor` commands and notebook paths are checked too.
- A throw in `tool.check` refuses the call with `CHECK_FAIL`. The `classic.PermissionRequest` hook answers only when the engine gave none, and a throw there leaves the normal dialog (`block.ts:127`, `:164-171`).
- A new user prompt clears the denial count, so a denial does not carry into the next request (`denied.ts:59`).

The baseline's classifier allow settled a gate ask, except a `person` ask such as the push-host ask (`block.ts:138-141`, `findings/push.ts:30`). Neither is carried: the rebuild has no classifier of its own, and `gate/rules.ts:125` asks on a forced push only (`parity.md`, row "gate push").

Alternative: keep the whole 4,677-line gate. Rejected: probe 2.8 shows that deny rules stop the plain form of every rule, so the gate's own copy of those paths only adds code.

### The dangerous-command list is shellfirm's rules, generated, with claudetto's extras as a patch

The user's direction (2026-11-06): "instead of using claudetto's own list. it finds the upstream lists somewhere, combines them into a unified file that can be generated to settings.json or whatever claudetto reads without re-inventing the wheel, and then the claudetto's extras become "patches" on top." And: "blocking more is fine as long as it keeps the agent away from becoming freaky and ruining things. your agents can probe which ones are genuinely bad." This replaces the earlier decision to vendor `agenttrailhq/guardrails` (27 of 42 caught, no evaluator, a TS file to import); that decision is deleted, not kept as a second path.

Survey of 2026-11-06 (tarballs in `/tmp/probe-cmds-*`, read as data, no code of theirs run). Four lists were measured: pleme-io/guardrail (2,447 YAML rules, 2,250 of them one generated AWS pattern), agenttrailhq/guardrails (74 TS rules), `kenryu42/cc-safety-net` and `Dicklesworthstone/destructive_command_guard` (rules are code; `dcg`'s license rider withholds rights from Anthropic). The data list with fixtures for every rule in both directions and a permissive license is kaplanelad/shellfirm (Apache-2.0): YAML rules in `shellfirm/checks/*.yaml` (`id`, `test` regex, `severity`, `filters`), fixtures in `shellfirm/tests/checks/*.yaml` (`test`, `expect_ids`).

Decision. `scripts/vendor-rules.ts` (run by `just vendor-rules`, the only way to change the generated file) downloads the tarball at commit `f9a867dd05a9467f6550f6228a62c33d5c37ce23` into a fresh temp dir, checks its SHA-256 `d43ab61e72c05f80c4402fc0b01517d80db205089362fac109c210dff5893a51`, and reads only the YAML and `LICENSE` with `Bun.YAML.parse`; nothing from the archive is imported or run. It keeps the groups `fs`, `git`, and `shell` at severity High and Critical, drops `fs-strict:*`, applies `hooks/gate/rules.patch.json`, and writes `hooks/gate/rules.generated.ts` (source, commit, sha256, rules, fixtures whose ids all stay live) and `hooks/gate/rules.LICENSE` (SHA-256 `378e5d8d3ed832156354f698072f7a55d62d12db8c9364e1d205a65f6d38674c`). The output is `.ts` and not JSON because a hooks module may import only code files. `settings.json` Bash rules are globs and cannot hold these regexes, so the gate reads the generated file; it is not turned into permission rules.

Verdicts are shellfirm's: Critical denies, High asks. The patch is `{disable: [ids], override: [{id, decision, evidence}], add: [{id, decision, regex, feed?, description?}]}`. The generator fails when a `disable` or `override` id matches no upstream rule, and an override must carry its evidence, a probe showing the rule hits a harmless command. No override and no disable is needed so far. Four rules are added, each for a measured gap: `claudetto:git-push-force-with-lease` (ask), `claudetto:write-system-path` (deny; neither survey list reads a redirect or `tee` into a system folder), `claudetto:rm-recursive-home-slash` (deny; upstream reads `~` and not `~/`), and `claudetto:download-piped-to-shell` (ask; upstream names bare `bash|sh|zsh|fish`, not `dash`, `ksh`, `/bin/sh`, `sudo -E bash`, or `env sh`).

Feeding. A rule's `feed` is `raw` (the whole command text; the `shell` group, which reads pipes) or `parsed` (each command from `shell-words.ts`, re-quoted, redirects appended, wrappers such as `sudo` stripped). After `--` a word that starts with `-` is fed as `./-word`, so `rm -- -r /` passes. A git command is fed as written and again with the options before the verb removed, so `git -C /tmp push --force` is judged as `git push --force`. `Matches` and `NotMatches` filters apply to the fed text; `PathExists` is ignored, because the gate does not stat paths. A command the parser cannot read still meets the raw rules and otherwise asks (`GATE_UNREADABLE`). The reason text is `<rule id>: <description>`.

Measurement. Hypothesis: shellfirm's High and Critical rules, fed this way, catch what `rules.ts` denied or asked and pass what its tests required to pass. Prediction: at least 35 of 42 caught, at most 2 of 39 flagged. Commands: `bun /tmp/probe-cmds-scripts/tbl.ts` (old judge reconstructed at `/tmp/probe-old/rules-old.ts`) and `bun /tmp/probe-cmds-scripts/cls.ts` for the fixtures. Result: 42 of 42 caught and 3 of 39 flagged, so the second half of the prediction fails by one, and the three are stricter on purpose: `git checkout .` asks (`git:checkout_discard_all`, it discards every unstaged edit), `curl ... | sh -c 'echo'` and `curl ...; ls | sh` ask (`shell:curl_pipe_to_shell`, a raw-text rule that cannot tell the pipe is unrelated). Each stays an ask, which is the cost of a question and not of a block. Across the kept rules' own fixtures, 586 commands change verdict toward stricter than the old gate, grouped by rule id in `/tmp/probe-cmds-scripts/before-after.tsv` (for example `git:branch_delete_force`, `git:stash_clear`, `fs:recursively_chmod`, `fs:recursively_chown`); about 9 are looser (the dry-run forms `-n`, `--force-with-lease -n`, `--force-if-includes`), which the old gate flagged and shellfirm's rules clear, and `git clean -fdn` was checked as a dry run that deletes nothing.

Fixtures. 1,122 of shellfirm's 2,657 fixtures concern a kept rule. `hooks/gate/upstream.test.ts` runs them: 648 positives hit every `expect_ids` id, 20 are `fs:windows_*` (no Windows command reaches the gate), 7 do not parse and meet the unreadable ask, and 28 are skipped by name with a reason because the Rust matcher does something the port does not (find expressions with negation or `-prune -exec`, a dry-run or read segment piped to a shell, a download that reaches an interpreter through a file or a substitution, zsh `=git`). The 419 negatives are clean except 5 named ones, where the patch is stricter or a Rust-only filter would clear the command. The same file asserts the 42/39 table with the new verdicts. The skip list is exact, so a fixture that starts to pass changes the counts and fails the lab.

`rules.ts` keeps what no list covers: `Read`/`Write`-over-Bash (5.15), the package rules of `packages.ts` (5.31), the hook-write ask, and `systemPath` for `Write` and `Edit` in `gate.ts`. Deleted with their tests and texts: `rootDelete`, `ROOTS`, `gitVerdict`, `gitParts`, the download ask, `GATE_ROOT_DELETE`, `GATE_DOWNLOAD_RUN`, `gateLosesWork`, `GATE_PUSH_REWRITE`.

Not run: `cc-safety-net` and `dcg` (an install or a build); pleme's Rust engine (cargo); shellfirm's own binary.

### Secret matcher

Goal item 1 makes betterleaks the one secret matcher. `hooks/secrets.ts` runs `betterleaks stdin -f json -r - --no-banner -l error --exit-code 0` through `$.process.run` and replaces each reported `Secret` with `[REDACTED]`. The gate's `tool.call` hook on every tool scans each result before the model sees it. The handoff writer and the handoff read-back scan their text before they write or inject it. `hooks/gate/env.ts`, `hooks/handoff/secrets.ts`, their tests, and the `.env` rules of `gate/rules.ts` are deleted.

Pin: betterleaks 1.10.0 (MIT). Homebrew's formula `betterleaks` has stable 1.10.0 and no versioned formula (`brew info --json=v2 betterleaks`), so `brew install` cannot hold a version. `SCANNER_VERSION` is the tested one, and `hooks/secrets.spec.ts` fails when the binary on `PATH` reports another (`betterleaks version`).

Probes of 2026-11-06 against the release binary at `/tmp/probe-bl/bin/betterleaks`:

- Exit codes. Hypothesis: findings and errors share exit 1 by default. Prediction: with `--exit-code 0`, a clean scan and a scan with findings exit 0, and a bad config exits 1. Result: as predicted. So `secrets.ts` reads exit 1 as a failed scan, never as findings.
- Config precedence. `-c` wins over `BETTERLEAKS_CONFIG`/`GITLEAKS_CONFIG`, which win over the inline `BETTERLEAKS_CONFIG_TOML`. Prediction: with both path variables set to `""`, the inline TOML is used. Result: it is, so a user's own config cannot replace claudetto's.
- Default rules. Prediction: the defaults catch an Anthropic `api03` key and miss the OAuth `oat01` form. Result: the defaults miss the OAuth token, an AWS secret key without its key ID beside it, a URL's password, and an `Authorization` bearer token. The inline config adds four rules (`anthropic-any-key`, `aws-secret-access-key-assignment`, `url-userinfo-password`, `authorization-header`) over `[extend] useDefault = true`.
- Coverage. With the extension, betterleaks and gitleaks 8.30.1 both catch all 10 secret lines of a made-up fixture and all 4 keys in the repo's `.env` (lines 5, 8, 11, 14; values not read, shapes only). A negative fixture (`DATABASE_HOST=localhost`, `PORT=5432`, `https://example.com/a@b`, `sk-ant-docs`) gives 0 findings. The first Anthropic rule, `sk-ant-[a-z]+\d{2}-`, missed `.env` line 8, an `sk-ant-` key without the `api03` form. The rule is now `sk-ant-[a-z0-9]+-`, which catches it. gitleaks is not needed, because betterleaks passes.
- Cost: about 40 ms per warm scan of a small result, and 0.41 s on 5 MB.

The lab cannot run a process (its `$.process.run` reaches only test hooks), so the lab tests the wiring with `hooks/secrets.mock.ts`. `hooks/secrets.spec.ts` runs the real binary under `just test`.

A scan that cannot run fails closed. A missing or failing binary rejects with `secretScanFailed`, which names `brew install betterleaks` and `/claudetto:setup`. The gate's `.catch` then denies the call, so the result is withheld, and a handoff is not written. The `.catch` first replays `next(e)`, so an error from the chain beneath is re-raised unchanged. Setup lists betterleaks as a required tool: its launch notice shows at every start while it is missing, and a decline is not recorded.

### One run-limits owner

The identical-failure and heavy-context refusals move from the gate's hook (`gate/block.ts:83`, `:99`) into the run-limits code. Both run on `tool.check` but are registered by run-limits, so their counting, settings, and refusals live in one place. They keep their defaults (12 starts per 600 s, 20 calls, 400,000 heavy tokens, 3 identical failures) and fail open on a state fault, because they guard spend and a refusal on every fault would stop all work (`gate/block.ts:74`). The subagent cap is read from one place, Claude Code's own `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` env setting (`hooks/limits/hold.ts:15`); the option and the tier row are dropped, because the native setting already covers them. Setup writes that setting by plan: 3 for Pro, 4 for Max, and none for Ultra, which has no 5-hour window (`hooks/setup/settings.ts`, `capGroup`).

### The Stop check verifies blockers, not words

The `run-limits` delta specifies alternative (b) from `ISSUES-2026-11-04-0934.md`, "Item 1". A blocker counts when the hook can check it: a `! <command>`, a denial in this turn's tool results from `$.session.messages()`, or an open `AskUserQuestion`. An open item is a Markdown task item `- [ ]` in the final reply, and an offer is a reply whose last line ends in `?`: both are defined syntax, so no word decides. The root prompt and the output style do not teach the task-item form (the user, 2026-11-06: they "should not have to deal with it"); the lean apply skill does, in `lean-openspec`, "Open Work as Task Items", so the check sees items where that workflow wrote them. A `userConfig` switch turns the check off. Probe 2.6 showed that the rows at Stop hold this turn's tool results with `isError`, and that no field marks a denial. A permission rule's denial has a fixed text, and a mod's denial is its reason in `<tool_use_error>`, the same wrapper a plain tool error gets. So the check matches the permission-denial texts, and the gate records its own denials by `tool_use_id` for the check to read (`ISSUES-2026-11-04-1500.md`, "Probe 2.6").

Alternatives: (a) wider word lists, rejected because each word is one more escape (probe rows 3 to 6). (c) A model grader, a Non-Goal.

### Handoff has one writer

The `handoff` hook is the only writer under `.claude/claudetto/handoffs/`. The compaction handover path calls it, and `/claudetto:handoff` keeps asking the model for the tool as its last call. Three token values touch this path, and they stay separate settings, because each one drives a different mechanism:

- `handoverThresholdTokens`, default `min(400000, window/2)`: from this size, a turn's end forks the conversation for a handoff (`plugin.json`).
- `HANDOFF_TRIGGER_TOKENS`, 140,000, or 90,000 on Haiku rows: setup turns it into `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, Claude Code's own compaction trigger (`threshold.ts:14`, `:57`, `tiers/snippet.ts:128`).
- `heavyContextTokens`, default 400,000: the run-limits refusal above.

Decision (task 5.7, 2026-11-06): 0.4.0 keeps that order. At the baseline defaults the autocompact trigger fires before the handover threshold, so the handover runs only where the user raised the trigger or set `handoverThresholdTokens` below it. The `compaction-path` run (`ISSUES-2026-11-04-1500.md`, "Task 5.7") priced a handover fork at about $0.10 per million context tokens and the built-in `/compact` at about $0.17, a gap of about $0.005 at 50,000 tokens, which is too small to move a default; and `claude -p` exits at the turn's end before the handover's timer runs, so the handover itself was not measured. There is no cheap summary: it has no option and no code.

### Engineering constraints from the goals

These come from `goals/ARCHITECTURE.md` and hold for every hooks module of 0.4.0:

- Each registration is a literal `on('<event>', ...)` call with direct `$.<namespace>.<method>()` calls, because the Mod validator reads them statically. No loop, proxy, or wrapper registers a hook, and no handler destructures `$`.
- Types come from the declarations that Claude Code generates in `.claude-plugin/types/`. Task 5.12 picks how CI reaches them.
- The TypeScript flags stay as strict as the baseline's: `strict`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes`.
- `claude plugin test` and `claude plugin validate` check each plugin. Pure policy functions get their own `*.test.ts` files.
- Agents keep their Greek names.

How much of Claude Code stays vanilla, item by item, is in `vanilla-research.md`.

### Features the user decides

The own classifier (`classify`) and Jev (`decide`) wait on the user's decision. The classifier decision reads the `just eval --classifier` results. For `decide`, the user set the route: where typesafe.ai's docs put Jev. The docs put Jev in code that asks it for a decision, not in the agent's model seat, and they set higher thresholds for riskier actions (`docs.typesafe.ai/introduction/coding-agents.md`, `patterns/probability-routing.md`). The baseline tool fits that route and sends only the model's question and option texts. The remaining choice is the call site, and the evidence for each is recorded in `ISSUES-2026-11-04-1500.md`, "Jev":

- The tool, as at the baseline: the model decides when to ask. One MCP route measured that "Haiku with the loose prompt called `jev_ask` in 5 of 6 runs", with the miss kept in its report (`lhviet/jev-bridge` README, opened 2026-11-04).
- A hook, as `Brainwires/jevwire` 0.6.6 does (read at `7089374`): `PreToolUse`, `PostToolUse`, and `Stop`, with a 1,500 ms Jev deadline inside a 5 s hook timeout. It fails open in silence, and it never answers `allow`, because Jev is not hardened against injection. A claudetto hook would add 152–262 ms warm to every gated call, and a first call measured 0.2–1.8 s (live calls, 2026-11-04). Two calls do not show whether that cold cost recurs once per session, per connection, or after idle time. A 1.8 s call misses a 1,500 ms deadline, so a hook in jevwire's shape fails open on it.

The 10 s hook budget bounds neither route. Waiting on `$.http.fetch` stops the hook clock, even with a `$.clock.sleep` raced beside it, and the fetch has its own 30 s cap that cannot be cancelled (`ISSUES-2026-11-04-1500.md`, "Probe: hook budget against Jev calls"). So each call site sets its own wall-clock deadline.

Recommended: keep the tool. Each point comes from the evidence above:

- It is the route typesafe.ai describes: code that asks Jev for a decision, with the risk threshold set by that code. The docs document no hook or MCP route.
- A hook could only deny or ask, never allow, and that work already belongs to the gate and the native `autoMode` classifier (2.8, 2.8b). It would add Jev's latency, and a hung call, to every gated tool call.
- The tool's cost falls only on the calls the model chooses to make, and the measured miss rate of that choice is 1 in 6 on Haiku.
- The rebuild keeps the baseline tool and changes three things: it thresholds `probabilities[choice]` at 0.75, the baseline's bar at two options, which no longer falls as options are added. It drops the per-try timeout from 12 s to 5 s, nearly 3 times the slowest call measured (1.8 s). A hung server then costs 5 s instead of 12 s, and the worst case, two slow 429 or 529 replies, falls from 39 s to 18 s. It keeps the 429/529 backoff and, like the baseline, does not retry a missed deadline (`specs/decide/spec.md`). Task 3.2 records the user's yes or no.

Whichever call site survives reads Jev's answer the way the docs advise. It thresholds a Choice on `probabilities[choice]`, not on `confidence`. `confidence` is `(p_max − 1/n)/(1 − 1/n)`, measured on 2, 3, and 4 options, so the baseline's floor of 0.5 lets a weaker top choice through as options are added: 0.75 with 2 options, 0.625 with 4 (`patterns/probability-routing.md`, "Why not `confidence`?"; `ISSUES-2026-11-04-1500.md`, "Jev"). The approval Noul keeps its P(yes) bound of 0.2. The 429 and 529 backoff stays (`api/errors.md`). A hook call site gets one try with its own short deadline, such as jevwire's 1,500 ms, because the hook limit does not count fetch waits. The deadline only stops the wait: `$.http.fetch` takes no `signal` on 2.1.318, so the request stays open up to its 30 s cap. Warm calls measured 152–262 ms, and cold calls 0.2–1.8 s.

The classifier and `decide` share the Jev client (`postJev` and `keyOf` in `decide/api.ts` and `decide/options.ts`). Whichever survives owns it. Until the user decides, each stays out of the rebuild, and its options (`classifierModel`, `typesafeApiKey`) stay pending.

## Stop grader (`gradeBlock` in `hooks/limits/stop.ts`)

Stop runs one Haiku call after the stall, named-files, and open-items checks, only when none of them blocked and `stop_hook_active` is false. A finding counts only when its code is offered this turn and its quote is a substring of the reply. Codes: `unchecked` and `rules` (tool-less turns only), `credited`, `unfiled` (only when no `ISSUES*.md` was written this stretch), and `fallback`. ## Slice commits (`hooks/slices.ts`)

A Stop that leaves files this session wrote uncommitted is blocked once with `SLICE_COMMIT`, which lists them and asks for one revertable commit per finished slice. It runs outermost (`register.ts`), so it acts only when every other Stop check passed, and its `{ stop_hook_active: false }` matcher keeps it to the first Stop. It asks the permission chain about `git commit` first, so a user's no-commit constraint (the ledger's `no-commit` rule) or a deny rule turns it off. The files come from a record of the content hash each agent write left, with no mark in the file. A successful Edit, Write, or NotebookEdit hashes its file (`git hash-object`), wherever it lives, so a file in another repo counts. After each Bash call, one `git status --porcelain -z -uall` and one batched `git hash-object` sweep the cwd's repo: a path whose hash moved across the call, and that is not already recorded with that hash, becomes the agent's. At Stop, only a file whose hash still matches its record is checked, with `git -C <its folder> status --porcelain -- <file>`, and a failed git run passes. On each person prompt the same sweep runs once: a recorded path whose hash moved, or a changed path the agent never wrote whose hash differs from the last sweep, goes into the context once as `SLICE_OTHERS`, and leaves the record. A file dirty before the session and not moved is never the agent's. Lab: sixteen `slices.test.ts` tests; mutants of the deny check, the other-block check, the empty-status check, the Bash record, the hash match at Stop, and the never-written branch each fail a test. Live probe `/tmp/probe-148` (Haiku, $0.0019): after an edit to `a.ts`, the first Stop ran the commit check and `git status` (8 characters), the session went on to `git commit`, and the second Stop passed in 0.9 ms. With a trap `git` first on `PATH` (`/tmp/probe-131/bin`), the full lab made no git call. Not handled: a user edit between two Bash sweeps of one turn is taken for the agent's; a Bash edit in a repo other than the cwd's is not seen; a user edit to an agent-written file outside the cwd's repo is not announced, though Stop still leaves it alone; and a file changed back to the exact content of the last sweep is not seen.
