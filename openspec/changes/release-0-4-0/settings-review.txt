Effort Level Mechanics & Calibration

Anthropic's 5.5 series implements adaptive thinking governed by the effort
parameter (low, medium, high, xhigh, max) rather than fixed token budgets. The
parameter governs reasoning depth as well as the verbosity and frequency of
external tool calls.

  - 'low': Suppresses deep deliberation and minimizes intermediate tool
    invocations.
  - 'medium': Anthropic's platform default for Opus 5.5 and Haiku 5.5. Balances
    speed and latency while allowing multi-step reasoning when prompted.
  - 'high' / 'xhigh': Allocates deeper reasoning tokens and explicit pre-action
    planning before executing terminal commands or file edits.
  - 'max': Removes reasoning constraints. Independent benchmarks (Artificial
    Analysis, Stanford/Harbor Terminal-Bench) demonstrate that 'max' effort often causes
    token runaway—ballooning per-task output to upwards of 190,000 tokens. On
    structured evaluations like FrontierCode 1.1, 'max' effort scored lower (46.2%) than
    'xhigh' (52.1%) due to overthinking and unsolicited out-of-scope code
    refactoring.

Optimal Workload Mapping & Production Trade-offs

1. Claude Opus 5.5

  - Target Domains: Deep root-cause debugging across repositories, ambiguous
    architectural decisions, financial models, regulatory audits, and multi-step
    autonomous workflows requiring persistent judgment.
  - Optimal Effort Setting: 'medium' or 'highä.
  - Empirical Profile: In code review pipelines (e.g., CodeRabbit), Opus 5.5
    achieves significantly higher precision on subtle bug patterns without
    regressions on edge cases. Independent accuracy evals record Opus 5.5 at 66%
    factual accuracy versus Sonnet 5.5's 54%. Community runs confirm Opus avoids
    false positives in strict fact-checking where smaller models hallucinate
    errors.
  - Cost Caution: Fast mode doubles standard rates (8/40 per 1M); 'max' effort
    yields diminishing benchmark returns relative to token cost.

2. Claude Sonnet 5.5

  - Target Domains: Primary driver for everyday engineering, well-scoped
    features, UI/frontend development, document parsing, slide deck generation,
    and bounded agentic execution.
  - Optimal Effort Setting: 'medium' or 'high'. Avoid 'max' effort in production.
  - Empirical Profile: Operates 30%+ faster than Sonnet 5 with reduced iteration
    counts. At matched effort (xhigh), it achieves ~95% of Opus 5.5's reasoning
    performance at 50% lower base token pricing (2/10 vs 4/20).
  - Cost Caution: Artificial Analysis documented that when set to 'max' effort on
    complex agentic runs, Sonnet 5.5 burned an average of 193,000 output tokens
    per task
    (7.60/task), ending up *more expensive* per completed task than Opus 5.5 at standard effort (5.98/task).

3. Claude Haiku 5.5

  - Target Domains: Latency-sensitive pipelines, real-time customer routing,
    repository file tree indexing/grepping, context compaction, and
    high-frequency subagents.
  - Optimal Effort Setting: low to medium.
  - Empirical Profile: Matches Sonnet 5.5 in codebase symbol/file searches
    (e.g., 44/48 files located at $0.44 vs. $1.38). However, community testing
    and system card evaluations indicate higher hallucination rates on
    open-ended web research, document verification, and complex PDF extractions.
  - Cost Caution: The 100K token threshold acts as a pricing step: prompt inputs
    above 100K scale 5× in cost from $0.10/M to $0.50/M, and outputs scale from
    $0.50/M to $2.50/M. Agent loops appending rolling histories can
    unintentionally cross this threshold.

--- G. YAML traps against the real parser ---
Claude Code 2.1.318 parses frontmatter with Bun.YAML.parse (chunk-w64mkcdc.js, KH). If that throws, it
quotes each top-level "key: value" line whose value holds one of { } [ ] * & # ! | > % @ ` or ": " and turns
leading tabs into spaces, then parses again (HMn and Bm). Table: /tmp/probe-yaml/yaml-traps.ts on bun 1.4.4,
which replays the same two steps. The Bun inside the claude binary may differ in version.
Bun.YAML is YAML 1.2, so the "Norway problem" and the YAML 1.1 coercions in the paste are WRONG here:
   name: off / no / yes  -> stay strings.        name: true   -> boolean true.
   version: 1.0          -> number 1.            build: 0124  -> 124 (not octal 84).
   released: 2026-11-04  -> stays a string.
Rescued by the fallback (load correctly, no warning on screen): "a: b" colon in the value, and a value that
   starts with @ ` % * [ { | >.
Silent data loss (parses, wrong value, no error):
